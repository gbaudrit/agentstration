# FlowRun: operational inspection and response retention

`/flow-runs/{RunId}` consumes the persisted FlowRun execution record, not a mutable Resource definition. FlowRuns.cs has execution/definition scopes, historical definition/version and runtime events; this route has no resource UID/metadata/namespace or definition-save, generic policy or YAML-authoring contract. Preserve its specialized shared ResourceDetailsTemplate shell and Overview/Worker/Causality/Activity/Handoffs/Input-output/Raw-events navigation, including supported strategy distinctions. Do not invent a definition form, activation, resource-owner badge, labels, policy administration or creation wizard. Execution scope and the qualified Flow reference retain their business meaning. Status/duration metrics precede the actual execution Identity and saved Configuration.

One ResourceSectionState now drives accepted and visited views; there are no parallel mutable tab/visited registries. Shared typed loading/refresh/error/retry replaces family load-state branches. Refresh retains the topology, visited panels, selected diagnostics and unsent human response through recoverable failure/retry. The response remains protected by the existing live leave guard and clears only for a new input request, accepted submission or invalidated execution. Lost access/missing/replaced run scope clears private input/output, pending response, causal/contract records and event/replay state; old and disposed responses cannot populate another run. Runtime cancel/respond, scoped replay/reconnect, bounded causal reads, token usage, immutable historical versions and authorization stay family-owned and unchanged.

Initial inspection remains busy until its auxiliary input/causality/history/realtime initialization has completed. Refresh cannot start while that initial replay is pending, including when internal event reconciliation reads the authoritative run. No resource loader, permission framework or business counter is added.
